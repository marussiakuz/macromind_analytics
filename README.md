# MacroMind Analytics

Платформа для предварительной проверки компаний и оценки инвестиционных проектов.
Объединяет сведения реестров, финансовую отчётность, исследование рынка и конкурентов.
Есть база знаний с поиском по тексту и смыслу — RAG.

**Статус: рабочий прототип в разработке.** Часть экранов использует демонстрационные данные.
Это ещё не готовый сервис для промышленной эксплуатации.
Описание обновлено **4 ноября 2026 года** по коду и локальным настройкам.
Настройки подключения не гарантируют, что удалённые процессы сейчас запущены.

## Что уже реализовано

| Модуль | Что есть в коде | Что нужно учитывать |
|---|---|---|
| Проверка компаний | Checko: поиск, реквизиты, руководители, учредители, финансы, реестры и история событий | Нужен ключ Checko; доступность отдельных методов зависит от тарифа |
| Проверка связанных физлиц | Деловые связи руководителей и учредителей через основной API | Это отдельный путь от поиска профилей людей |
| Анализ рынка и конкурентов | Поиск сайта, чтение страниц продукции, Exa/Tavily/Yandex Search, OpenAlex, локальная Qwen, ссылки, цитаты и версии отчётов | Основной поиск сейчас Exa; резерв Tavily выключен; качество на разных отраслях ещё проверяется |
| База знаний | PostgreSQL/pgvector, документы и фрагменты, очередь индексации, поиск, разграничение рабочих пространств | Требуются БД, миграции, процесс обработки очереди и отдельный сервис векторизации текста |
| Слабые сигналы | События, наблюдения, гипотезы и API базы знаний; есть подключение к интерфейсу | Не означает, что уже собран полный корпус источников; часть интерфейса использует демоданные |
| Поиск людей | Отдельный API: поиск кандидатов и профиль по явно выбранным аккаунтам | VK/LinkedIn требуют своих доступов; санкции, долги и суды этого сервиса не подключены |
| Заявки и воронка | Экраны фонда и стартапа, карточки проектов, формы и демонстрационные сценарии | Нет завершённого серверного процесса работы с заявками и полноценной авторизации пользователей |

Зелёные тесты подтверждают проверенные сценарии кода. Они не доказывают доступность внешних API
или качество рыночных выводов. После исправлений 4 ноября прошли 107 профильных тестов рынка, поиска и клиентов моделей.
Свежий полный отчёт через UI после этих исправлений ещё не проверен.

## Быстрый запуск без базы знаний

Нужны Python **3.10+**, Node.js **20+** и npm. Проверенная версия Python — 3.10.12.
Команды ниже выполняются из корня клонированного репозитория.
Для каждого сервиса откройте отдельный терминал.

### 1. Основной API

```bash
cd backend/osint-agent
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
cp .env.example .env
# Для реальных проверок задайте CHECKO_API_KEY в .env.
.venv/bin/python -m uvicorn osint_agent.main:app --host 127.0.0.1 --port 8000
```

API: http://localhost:8000/docs. Проверка процесса: http://localhost:8000/health.
Без ключей процесс запускается, но реальные проверки недоступны.
Redis необязателен для базового запуска: при недоступности кэш использует запасной режим.
Пустая SQLite-база рынка создаётся при первом обращении.

### 2. Интерфейс

```bash
cd front
npm ci
cp .env.example .env
npm run dev
```

Откройте http://localhost:5174. Демо-вход указан на экране входа.
Для реальной проверки выберите «Фонд → Проверить юр. лицо» и введите ИНН.
Рыночный раздел находится после финансовой отчётности.
Основные API-адреса пока заданы в коде: `localhost:8000` и `localhost:8001`.
Интерфейс нельзя просто разместить на другом домене без изменения этих адресов и CORS.

### 3. Поиск людей — при необходимости

```bash
cd backend/person-osint-agent
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
cp .env.example .env
.venv/bin/python -m uvicorn person_osint.main:app --host 127.0.0.1 --port 8001
```

API: http://localhost:8001/docs. Для проверки руководителей через Checko этот сервис не нужен:
её выполняет основной API на порту 8000.

**После переноса каталога создавайте окружения заново.** Старые `.venv` могут содержать
абсолютные пути к прежнему расположению. Не переносите их в Git.
После изменения `.env` перезапускайте процессы. `--reload --reload-dir src` допустим
для локальной разработки, но не гарантирует перечитывание `.env`.

## Модели и их задачи

| Модель | Задача | Подключение и состояние |
|---|---|---|
| **Qwen3.5-4B**, файл `Qwen3.5-4B-Q4_K_M.gguf` | Определяет продукт компании, готовит интерпретацию и проверяет соответствие выводов источникам | Текущий локальный вариант. Отдельный процесс `llama-server` на сервере 2, совместимый с OpenAI Chat Completions API |
| **Qwen/Qwen3-Embedding-0.6B** | Превращает фрагменты документов и поисковые вопросы в числовые векторы | Отдельный HTTP-сервис на сервере 2. Векторы размерности 1024 сохраняются в PostgreSQL/pgvector |
| **urchade/gliner_multi-v2.1** | Находит упоминания компаний, продуктов, технологий и покупателей | По отчёту развёртывания — отдельный сервис на сервере 1. В репозитории есть клиент и тесты; загрузка питч-деков с полной обработкой ещё не завершена |
| **Qwen3.6-35B-A3B через Yandex Studio** | Прежний облачный вариант генерации | Адаптер сохранён. Выбирается через `LLM_PROVIDER=yandex`; нужны рабочие доступы Yandex Studio |

`Q4_K_M` — сжатый формат весов модели, который уменьшает потребление памяти.
GLiNER использует многоязычную DeBERTa внутри модели. Отдельный процесс DeBERTa не нужен.
GLiNER находит упоминания, но не подтверждает факты и может не учитывать отрицание.

Генерация текста, извлечение сущностей и поиск по смыслу — три разные задачи.
Модель векторизации не пишет отчёт. Qwen для генерации не заменяет базу знаний.

### Размещение сервисов

| Узел | Сервисы | Адреса в текущей схеме |
|---|---|---|
| Сервер 1 — `192.168.1.12`, внутренняя сеть `10.77.0.1` | Целевое размещение приложения, PostgreSQL/pgvector, документы, обработчик очереди; GLiNER по отчёту развёртывания | PostgreSQL: `5432`; GLiNER: `127.0.0.1:8010` |
| Сервер 2 — `192.168.1.13`, внутренняя сеть `10.77.0.2` | Генерация Qwen через llama.cpp и сервис векторизации | Генерация: `127.0.0.1:8080`; векторизация: `10.77.0.2:8091` |
| Рабочая станция | Локальный интерфейс и API при разработке, SSH-туннели к моделям | UI: `5174`; основной API: `8000`; API людей: `8001` |

Для локальной разработки нужны доступные SSH-профили `server1` и `server2`.
Профили и SSH-ключи настраиваются отдельно и не входят в репозиторий.
Оставьте туннели работающими в отдельных терминалах:

```bash
# Генерация и векторизация через сервер 2
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -L 127.0.0.1:18080:127.0.0.1:8080 \
  -L 127.0.0.1:18091:10.77.0.2:8091 server2

# База знаний и GLiNER через сервер 1 — если они нужны локально
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -L 127.0.0.1:15433:10.77.0.1:5432 \
  -L 127.0.0.1:8010:127.0.0.1:8010 server1
```

На сервере 2 модель запускается отдельно от основного приложения:

```bash
~/llama.cpp/build/bin/llama-server \
  -m ~/models/Qwen3.5-4B-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8080 -c 16384 -np 1 --no-warmup --jinja
```

Эта команда предполагает установленный llama.cpp и заранее скачанные веса.
Файлы модели не входят в репозиторий. На CPU генерация может занимать несколько минут.
Одного запуска FastAPI недостаточно: процессы моделей и туннели должны работать отдельно.

### Настройки основного API

Файл: `backend/osint-agent/.env`. Ниже — пример текущей локальной схемы без секретов:

```ini
DEMO_MODE=false
CHECKO_API_KEY=

LLM_PROVIDER=local
LLM_BASE_URL=http://127.0.0.1:18080/v1
LLM_MODEL=qwen3.5
LLM_CONTEXT_SIZE=16384
LLM_MAX_TOKENS=2000
LLM_TIMEOUT_S=600

SEARCH_PROVIDER=exa
EXA_API_KEY=
SEARCH_FALLBACK=false
SEARCH_FALLBACK_PROVIDER=tavily
SEARCH_FALLBACK_BUDGET=2
TAVILY_API_KEY=
TAVILY_SEARCH_DEPTH=advanced
OPENALEX_API_KEY=

EMBEDDING_BASE_URL=http://127.0.0.1:18091
EMBEDDING_MODEL=Qwen/Qwen3-Embedding-0.6B
EMBEDDING_DIMENSION=1024
GLINER_BASE_URL=http://127.0.0.1:8010
```

Пустые значения ключей нужно заполнить своими доступами.
`LLM_MODEL=qwen3.5` — имя в запросе API; фактические веса задаёт команда запуска llama-server.
`LLM_MAX_TOKENS` — базовая настройка. Рыночный конвейер отдельно задаёт лимит ответа из размера контекста.
При замене модели меняйте веса сервера, `LLM_MODEL` и `LLM_CONTEXT_SIZE` согласованно.
Если новый сервер поддерживает этот же API, переписывать сбор фактуры не требуется.
Качество новой модели нужно проверить на одинаковых компаниях и источниках.

Поиск выбирается через `SEARCH_PROVIDER=exa`, `tavily` или `yandex`.
Tavily используется как резерв только при `SEARCH_FALLBACK=true`.
Основной и резервный поиск учитывают общий бюджет запросов исследования.
Yandex Search требует `YANDEX_API_KEY` и `YANDEX_FOLDER_ID`.
Для облачной генерации переключите `LLM_PROVIDER=yandex` и настройте Yandex Studio.
TechTrendSearcher для прямого обращения к поисковым API и OpenAlex запускать не нужно.

Секреты храните на стороне API. Любая переменная `VITE_*` доступна пользователю браузера.
Не помещайте туда ключи поставщиков или `KNOWLEDGE_INTERNAL_TOKEN`.
После изменения `.env` перезапустите соответствующий процесс.

## Как формируется отчёт компании

1. Пользователь вводит ИНН в разделе проверки юридического лица.
2. Основной API получает из Checko реквизиты, финансы и доступные данные реестров.
3. Исследование ищет официальный сайт и читает страницы продукции.
4. Модель определяет продукт, применение, покупателей и направления бизнеса по найденным источникам.
5. Система строит русские и английские запросы о рынке, технологиях и возможных конкурентах.
6. Exa собирает ссылки и выдержки. OpenAlex добавляет научные публикации и аннотации.
7. Загрузчик читает доступные страницы и PDF. Система удаляет дубли и сохраняет происхождение фактуры.
8. Qwen готовит разделы рынка, рисков и конкурентов с идентификаторами источников.
9. Код проверяет цитаты, числа и дубли. Дополнительная проверка моделью оценивает соответствие выводов источникам.
10. Версия отчёта сохраняется. Интерфейс показывает её после финансовой отчётности и позволяет скачать HTML.

При повторном открытии интерфейс сначала запрашивает сохранённый отчёт.
Это не новый поиск и не повторная генерация. Для проверки изменений запускайте новое исследование.

Кандидат из поиска ещё не считается подтверждённым конкурентом.
Нужно подтвердить сходство продукта и применения источниками о самом кандидате.
Судебные связи, закупки и общий ОКВЭД сами по себе конкуренцию не доказывают.
Общую выручку компании нельзя автоматически считать продажами одного продукта или объёмом рынка.

Если данных недостаточно, раздел может остаться пустым с объяснением причины.
Статус `partial` означает неполный результат; `insufficient_data` — недостаточно подтверждённых данных.
Частичный сбой проверки выводов получает статус аудита `partial`, а не `completed`.

Перед поиском локальный клиент проверяет `/health` модели с тайм-аутом пять секунд.
Если модель недоступна или не отвечает вовремя, API возвращает ошибку 503.
Такой сбой не сохраняется как новый пустой отчёт; прежняя версия остаётся доступной.
Интерфейс показывает текущий этап через `GET /api/v1/market/auto-analysis/progress?request_key=…`.
Маршрут возвращает только статус, этап и время обновления.

Поле `stage_timings` содержит длительность этапов, а `model_calls` — время и расход токенов каждого вызова.
Тексты запросов в эти поля не записываются.
Для одного подтверждённого направления с доверенного сайта система повторно использует полученный профиль.
Многопрофильный или неподтверждённый бизнес проходит отдельное определение профиля.
Финальные проверки цитат и выводов сохраняются.


Основные точки кода:

- `backend/osint-agent/src/osint_agent/market/universal_analysis.py` — последовательность исследования.
- `backend/osint-agent/src/osint_agent/market/analytical_report.py` — генерация, проверка и HTML отчёта.
- `backend/osint-agent/src/osint_agent/market/providers/` — клиенты моделей и поисковых сервисов.
- `backend/osint-agent/src/osint_agent/market/research_budget.py` — общие лимиты исследования.
- `front/src/market/events.js` — запуск исследования и восстановление сохранённых результатов.

## Как работает база знаний — RAG

RAG — поиск подходящих материалов перед подготовкой ответа моделью.

Документ сохраняется вместе с адресом источника, датой и правами доступа.
Затем текст делится на фрагменты. Модель Qwen3-Embedding создаёт для них векторы.
Векторы хранятся в PostgreSQL с расширением pgvector, исходные файлы — в отдельном каталоге.
Поиск сочетает совпадения слов и смысловую близость фрагментов с учётом рабочего пространства.

Параметры подключения: `KNOWLEDGE_DATABASE_URL`, `KNOWLEDGE_OBJECTS_ROOT`,
`KNOWLEDGE_INTERNAL_TOKEN` и `KNOWLEDGE_USER_ACCESS`. Образец находится в `.env.example`.
Для базы нужны миграции из `backend/osint-agent/migrations/` и отдельный обработчик очереди:

```bash
# Из backend/osint-agent/; параметры запуска показывает справка
.venv/bin/python -m osint_agent.knowledge.worker --help
```

Рыночный отчёт сейчас собирает внешние источники напрямую и сохраняет их в версии отчёта.
Наличие базы знаний не означает, что каждый рыночный отчёт автоматически использует её поиск.
GLiNER пока имеет отдельный клиент; полная цепочка загрузки PDF/PPTX и выделения сущностей ещё дорабатывается.
Заявления из питч-дека нужно хранить отдельно от независимо подтверждённых фактов.

## Проверки

```bash
# Из front/
npm test
npm run build

# Из backend/osint-agent/ с тестовым .env без рабочих ключей и серверных адресов
.venv/bin/python -m pytest tests/unit tests/knowledge tests/integration/test_full_pipeline.py -q

# Из backend/person-osint-agent/ с тестовым .env
.venv/bin/python -m pytest tests/unit tests/integration -q -m 'not integration_real'
```

Тесты PostgreSQL требуют отдельной тестовой БД с миграциями. Без БД они могут пропускаться.
Не запускайте их против рабочей базы. Полный запуск `pytest` может затронуть сеть или внешние сервисы.
Для воспроизводимости используйте тестовый `.env` без рабочих ключей и адресов баз.

## Как продолжать разработку

Сначала проверьте основной API и доступность нужных поставщиков.
Затем запустите профильные тесты и свежее исследование через интерфейс.
Проверьте принадлежность сайта компании, содержание цитат и источники каждого конкурента.
Проверка старого сохранённого отчёта не заменяет новое исследование.

Следующий этап — завершение загрузки питч-деков, извлечения текста и сущностей через GLiNER.
До него нужно подтвердить качество текущего отчёта на компаниях из разных отраслей.
Локальные планы в `docs/` могут отсутствовать у другого разработчика, поскольку каталог игнорируется Git.

Лицензия: метаданные Python-пакетов указывают MIT, но отдельного файла LICENSE пока нет.
Перед публичным распространением владелец проекта должен подтвердить выбранную лицензию.
