# Передача проекта разработчику

## С чего начать

1. Прочитайте главный README и `docs/VERIFICATION.md`.
2. Выполните установку в новых окружениях. Не переносите старые `.venv` и `node_modules`.
3. Проверьте `/health` обоих API и сборку интерфейса.
4. Подключите свои ключи Checko, Yandex и OpenAlex. Проверяйте каждый источник отдельно.
5. Выполните новый запрос компании и убедитесь, что появилась новая версия отчёта.
6. Откройте тот же результат повторно. Повторное открытие не должно обращаться к модели.
7. Только затем подключайте базу знаний и проверяйте загрузку, индексацию и поиск.

Временные журналы старой установки и сведения об удалённых серверах не заменяют этот порядок.
История разработки вынесена за пределы папки проекта. Новый разработчик не должен зависеть от неё.

## Текущие ограничения

### Приоритет 1: живой анализ рынка

Последний подтверждённый живой прогон завершался HTTP 401 от поиска и модели Yandex.
Причина требует проверки доступов: нельзя утверждать, что ключ именно «истёк», без подтверждения поставщика.
После восстановления доступа нужен новый прогон по нескольким ранее не проверенным компаниям.
Сохранённые отчёты из рабочей SQLite не входят в Git и не доказывают качество нового запуска.

Поиск конкурентов пока не гарантирует покрытие рынка и правильность всех классификаций.
В `competitor_research.py` сохраняются эвристики фильтрации названий; их независимость от отрасли требует проверки.
Его предварительные строки больше не должны вытеснять проверенные описания из интерпретации.
Проверяйте роли: разработчик, производитель, интегратор, перепродавец, поставщик.

`ResearchBudget` присутствует, но не все вложенные поисковые/модельные вызовы используют единый остаточный бюджет.
Общий лимит API сейчас составляет 300 секунд. Проверить фактическое число запросов,
тайм-ауты и сохранение промежуточных материалов при сбое — отдельная задача.

### Приоритет 2: завершить продуктовые сценарии

Воронка, загрузка документов стартапа, итоговый отчёт и часть слабых сигналов содержат демонстрационные сценарии.
Нужно определить серверные сущности заявок, права фонда и стартапа, хранение документов и версий решений.
Демо-вход интерфейса не заменяет авторизацию. Реестровые API также требуют контроля доступа
перед открытой эксплуатацией.

### Приоритет 3: база знаний

Проверить на отдельном стенде миграции, закрытость рабочих пространств, очередь, восстановление после сбоя,
повторную индексацию и резервное копирование вместе с файлами документов.
Пользовательский токен браузера не должен совпадать с сервисным токеном.
Сервис векторизации пока не проверяет токен, а версия модели не закреплена в фактической загрузке.

Качество поиска проверять на размеченных вопросах: учитывать точность подходящих фрагментов,
ложные совпадения и корректный отказ при отсутствии ответа. Нельзя заявлять численные показатели
качества без конкретного корпуса, версии настроек и сохранённого прогона.

### Приоритет 4: воспроизводимость и эксплуатация

- Зафиксировать проверенные версии зависимостей; сейчас Python-зависимости в основном имеют только нижние границы.
- Вынести адреса API фронтенда в общую конфигурацию.
- Разделить крупную сборку интерфейса и загружать тяжёлые экраны по необходимости.
- Отделить тестовые настройки от рабочих и исключить прямую запись тестов в рабочие БД.
- Автоматизировать проверки перед коммитом и после развёртывания.
- Подтвердить лицензию и добавить LICENSE. Метаданные уже упоминают MIT, но файла пока нет.

## Что считать готовым исследованием

- Входной ИНН и название относятся к нужному юридическому лицу.
- Продукт и применение определены по прочитанным источникам; роль компании не угадана по ОКВЭД.
- Рыночные оценки имеют автора, дату, валюту, единицы и границы сегмента.
- Конкуренты имеют конкретное описание продукции, основание сходства и соответствующий источник.
- Компания, её собственные продукты, сотрудники и награды не попадают в список конкурентов.
- Недостаток доказательств показан явно. Для заполнения отчёта модель не выдумывает числа или компании.
- Новая версия сохраняется и одинаково восстанавливается в UI и скачанном отчёте.
- Сбой источника отображается как сбой; старый отчёт не выдаётся за новый.

## Подготовка первого коммита

В рабочей папке Git ещё не инициализирован. До `git init` выполните из корня:

```bash
python3 scripts/check_publish.py
```

Скрипт использует временный служебный каталог Git и не создаёт `.git` в проекте.
Он проверяет будущий состав файлов, исключённые рабочие данные и совпадения с известными локальными секретами.
Это дополнительная проверка, а не полная гарантия отсутствия всех секретов.

При создании репозитория владелец выбирает видимость и лицензию.
После `git add` отдельно просмотрите `git status` и `git diff --cached --stat`.
`.gitignore` не удалит секреты, если они уже были добавлены в историю другого репозитория.
